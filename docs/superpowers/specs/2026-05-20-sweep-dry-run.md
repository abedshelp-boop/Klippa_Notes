## Open questions for Abed

Three cases where I want a second opinion before Phase 8 runs:

1. **`python-service/main.py:192-195, 228-230` — ASCII banner and the "Say 'Hey Deen' or
   press Ctrl+Shift+N" instruction lines at startup.** I categorized these as Bucket 2
   (delete) because they're decorative startup output, not diagnostics. But in dev mode
   the banner does double as a visual "Python service is up" signal in the terminal.
   - Option A: Delete (current plan).
   - Option B: Keep but route through `debug.log("Main", "...")` so it shows up in dev only.
   - Option C: Keep as raw `print()` because banner output is genuinely a startup-doorway
     marker for an operator watching the terminal.
   My instinct: Option A — Electron's `[Python]` stdout-pipe prefix already marks the
   service-up event, and the log file rotation already gives the operator the "ready"
   signal. But this is your terminal experience to decide.

2. **`python-service/ai_client.py:451-477` — the `DEEN_DEBUG_PROMPT` block.** This is an
   env-gated 12-print dump of the entire LLM prompt + response. It's already gated by
   `os.getenv("DEEN_DEBUG_PROMPT")` so it can't fire by accident. Routing through
   `debug.*` adds a second gate (dev mode) which means in a packaged build with
   `DEEN_DEBUG_PROMPT=1` set, you'd get **nothing** because `debug.log` no-ops in
   non-dev. That's almost certainly not what you want — you set the env var precisely
   because you want to see prompts in a packaged build to debug a regression.
   - Option A: Leave the block alone (don't route through `debug.*`); the env gate is
     the right control here.
   - Option B: Route through a separate `debug.dump(...)` helper that's always-on
     when the env var is set, regardless of dev mode.
   - Option C: My plan (route through `debug.log("ai_client", ...)`) but accept that
     `DEEN_DEBUG_PROMPT` is then a dev-mode-only switch.
   My instinct: Option A — the env gate is doing real work here that the dev-mode gate
   would break. Best to skip this block in Phase 8 and document it as "intentional
   bypass of the debug helper."

3. **`python-service/note_generator.py:219` — the top-level pipeline catch-all** (`except
   Exception` around the entire `process_note` body). The pipeline crosses
   Whisper/AssemblyAI/LLM/DB/disk subsystems. I've planned to keep the broad catch and
   add a justifying comment, but two narrower options:
   - Option A: Keep `except Exception` (current plan) — pragmatic safety net.
   - Option B: Catch each subsystem separately at each `await loop.run_in_executor(...)`
     site. More code, narrower errors, but loses the "always save pending" guarantee
     because a DB-write failure after a successful transcribe wouldn't trigger
     `_save_pending`.
   - Option C: Add a logging-but-re-raising wrapper at the outermost level so the FastAPI
     handler sees the error and returns a 500, instead of swallowing.
   This one is more of a design discussion than a sweep call. My instinct is Option A
   stays — but flagging in case you want a separate Phase to refactor this pipeline.

If you don't have strong feelings, I'll go with my instinct on each (Option A on all
three) in Phase 8.
